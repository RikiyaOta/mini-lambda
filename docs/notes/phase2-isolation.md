## 説明の控え(10-23、エージェントが書いたもの)

### namespace は種類ごとに別々のオブジェクト

1つの namespace が複数の性質を持つのではない。プロセスは種類ごとの欄を持ち、それぞれが1つの namespace を指す。
`unshare` に渡したフラグの種類だけ、新しいオブジェクトに差し替わる。書かなかった種類はホストと共有のまま。

```
子プロセス
  user   → 新しい user namespace   ← CLONE_NEWUSER で作った
  pid    → 新しい PID namespace    ← CLONE_NEWPID で作った
  mnt    → ホストと同じもの
  net    → ホストと同じもの
  uts / ipc / ... → ホストと同じもの
```

実物は `ls -l /proc/<pid>/ns/` で見える(`pid:[4026531836]` の番号が namespace の識別子)。

### `unshare` を呼んだ本人が「いつ入るか」は種類で違う

作られるのはどれも `unshare` の時点。

| 種類 | `unshare` を呼んだ本人 | その後に `fork` した子 |
| ---- | ---------------------- | ---------------------- |
| User | すぐに入る             | 入る                   |
| PID  | 入らない(PID は途中で変えられない) | 入る(最初の子が PID 1) |

### なぜ `sudo` なしでも PID namespace を作れたか

user 以外の namespace は、作られるときに「持ち主の user namespace」が決まり、作る権限はその持ち主の中での権限で判定される。

```
ホストの user namespace(最初からあるもの)
 └ 新しい user namespace   ← 作った本人はここで CAP_SYS_ADMIN を持つ
     │ 「所有」
     ▼
   新しい PID namespace     ← 親はホストの PID namespace
```

1. 同じ `unshare` 呼び出しの中で、user namespace が必ず先に作られ(`man 7 user_namespaces`)、本人はすぐその中に入る
2. 続けて PID namespace を作るとき、持ち主は新しい user namespace。そこでは `CAP_SYS_ADMIN` を持っているので許可される
3. `CLONE_NEWPID` だけのときは、持ち主がホストの user namespace で、そこでは `CAP_SYS_ADMIN` が無い → EPERM

中で手に入る権限は、その namespace の中だけで有効。外(ホスト)に対しては何の力も無い(`ps` で見ると `rikiyaota` のまま)。

### uid が 65534 になる理由

`uid_map`(中の uid と外の uid の対応表)を書いていないと、カーネルは対応する番号が無いものとして 65534(nobody)を見せる。
`unshare --map-root-user` は「中の 0 = 外の 1000」を書いてくれていた。

## 説明の控え(10-25、エージェントが書いたもの)

### 対応表は namespace に1つ

`uid_map` / `gid_map` はプロセスごとではなく、**user namespace ごとに1つ**。`/proc/self/uid_map` は「自分が属する user namespace の対応表」を見せる窓。

- `unshare(CLONE_NEWUSER)` の直後、呼んだ本人はもう新しい user namespace にいる(対応表は空 → uid は 65534)
- 本人が `/proc/self/uid_map` に書く → その namespace の対応表が決まる → 本人の uid も 0 になる
- `fork` した子は同じ user namespace にいるので、同じ対応表を使う(親子とも uid 0)

書き方は `<中の id> <外の id> <個数>` の1行。`sudo` なしで書けるのは**自分の uid / gid 1個だけ**なので、外の値は `unshare` の**前**に `getuid()` / `getgid()` で取っておく(後だと 65534)。どちらも1回しか書けない。

### `gid_map` の前に `setgroups` を `deny` にする理由

**グループはプロセスの持ち物。** ログイン時に `/etc/group` からコピーされ、`fork` で子に引き継がれる。
`id` の `gid=` がメインのグループ、`groups=` が**補助グループ**。ファイルを開くとき、カーネルはこのプロセスの一覧で権限を判定する。
`setgroups(2)` はこの補助グループの一覧を書き換えるシステムコールで、普通は `CAP_SETGID` が要る。

**危ない例**: グループだけを締め出すファイル

```
-rwx---rwx  owner=admin  group=banned   secret.txt
```

`banned` グループの人は何もできず、その他の人は全部できる。`banned` に入れられた人が、自分の補助グループから `banned` を**外せたら**、「その他の人」として判定されて読めてしまう。

**user namespace とのつながり**: namespace の中では誰でも全権限を持てるので、放っておくと `setgroups` で `banned` を外せてしまう。
そこで「`sudo` なしで `gid_map` を書くなら、先に `/proc/self/setgroups` に `deny` を書いて、グループを外す道を塞げ」という規則になっている。

- `/proc/self/setgroups` の初期値 `allow` は親の namespace からの引き継ぎ。`allow` のままでは `gid_map` を書けない(EPERM)
- 順番は `setgroups` に `deny` → `gid_map`。`gid_map` を先に書くと、もう `deny` にできない
- 一次資料: `man 7 user_namespaces` の「Defining user and group ID mappings」と「The /proc/pid/setgroups file」

## 説明の控え(11-03、エージェントが書いたもの)

### PID まわりの登場人物は3つ

| 名前 | カーネルでの名前 | 何か | 数 |
| ---- | ---------------- | ---- | -- |
| **プロセス本体** | `task_struct` | プロセスそのもの。uid、fd テーブル、所属 namespace、所属 cgroup などの持ち物を全部持つ | プロセス1つに1つ |
| **番号札** | `struct pid` | そのプロセスの PID を、namespace の段ごとに並べた一覧 | プロセス1つに1つ |
| **対応表** | PID namespace の中の表 | 「番号 → 番号札」を引く表 | PID namespace 1つに1つ |

```
 ホストの対応表                    子の namespace の対応表
 ┌──────────────┐                 ┌──────────────┐
 │ 1      → …   │                 │ 1 ─┐         │
 │ 200526 ─┐    │                 └────┼─────────┘
 └─────────┼────┘                      │
           ▼                           ▼
        ┌───────────────────────────────────┐
        │ 番号札 (struct pid)               │
        │   ホストでは 200526 / 子の中では 1 │
        └─────────────────┬─────────────────┘
                          ▼
        ┌───────────────────────────────────┐
        │ プロセス本体 (task_struct)        │
        │   uid, fd テーブル, 所属 cgroup … │
        └───────────────────────────────────┘
```

2つの対応表が、同じ1枚の番号札を別々の番号で指している。ホスト側からは `grep NSpid /proc/<pid>/status` で全段の番号が見える(例: `NSpid: 200547 2`)。

### この3つで言い直すと

- **`getpid()`**: プロセス本体 → 番号札 → 自分の段の番号を読む → 1
- **ホストから見た PID**: プロセス本体 → 番号札 → ホストの段の番号を読む → 200526
- **`cgroup.procs` に「1」と書く**: 書いた人(`current`)がいる namespace の対応表で 1 を引く → 番号札 → プロセス本体 → 所属 cgroup を付け替える
- **メモリの制限**: ページフォルトを起こしたプロセス本体(`current`)の所属 cgroup に計上する。番号札も対応表も使わない

`current` は「今 CPU 上で動いているプロセス」を指すカーネル内のポインタ。システムコールやページフォルトは呼んだプロセス自身の上で処理されるので、カーネルは誰の代わりに動いているかを最初から知っている(監視しているわけではない)。
fd 番号が「呼んだプロセスの fd テーブル」で引かれるのと同じ形。

一次資料: `include/linux/pid.h`(`struct pid`、`struct upid`)、`kernel/pid.c`(`alloc_pid()`、`find_task_by_vpid()`)。
Web では <https://elixir.bootlin.com/linux/v6.12/source/include/linux/pid.h> が読みやすい。

- User namespace は、プロセスから見える uid, gid を親のものと対応付けることができる。そのプロセス自身は uid=0 と思っているが、親の namespace 側から見ると、uid=1000 だったりする。
  - その対応関係は、`/proc/self/uid_map`, `/proc/self/gid_map` に記録する。

  - フォーマットは、1行毎に1つの対応関係を記録するもので、 `<内から見た uid/gid> <外から見た uid/gid> <個数>` である。
    - `<個数>` は、uid/gid から何個分を対応させるかを指定する。
  - なお、`/proc/self/gid_map` に書き込むには、`/proc/self/setgroups` を `"deny"` にしておく必要がある。これをすることで、その user namespace にいる全プロセスが `setgroups` syscall を呼ぶことができなくなり、特定のグループから自身を抜けさせるような操作ができなくなり、特定のグループに属しているユーザーに意図しない情報漏洩をさせないようにできる。

      - `setgroups` は通常、`CAP_SETGID` という権限が必要で、普通のプロセスはそれを持っていない。
      - が、`unshare(CLONE_NEWUSER)` で作った user namespace の中では、作ったプロセス自身が権限を持っており、さらに fork した子プロセスも同じ権限を引き継ぐので、誰でも全権限を持つことになり、`setgroups` を呼べてしまう。
      - よって、上のような制約が必要になる。
- Pid namespace は、プロセスから見える pid を親から見えるものとは別のものに対応させるもの。
  - 親から見れば普通のプロセスだが、子自身は pid=1 など、自分を特殊なプロセスと認識させることができる。

- 次に、cgroup に作ることのできるプロセス数を制限するために `pids.max` にプロセス数の上限を書き込み、制限をかけることを学んだ。
  - `myns.rs` では `sh -c "for i in $(seq 1 10); do sleep 777 & done"` のようなスクリプトを子プロセスで実行することで検証した。
  - 孫プロセスにあたる `sleep` が sh (pid=1) とは別プロセスとして起動するため、上限に達する。
  - ちなみに、sh 自身もカウントされるため、sh + sleep の個数を勘定する必要がある。
  - プロセス数の上限に達したとき、`fork` が失敗するようになる。
  - `sh` は `fork` が失敗すると、can't fork と表示して status code 2 で終了する。
  - 上限に当たったときは、単に fork が断られるだけというのがポイント。
  - 別の機構として、PID namespace では、pid=1 のプロセス (init process) が終了すると、その namespace に属するすべてのプロセスに対してカーネルが SIGKILL を送る。
  - なので、`sh` がエラーだろうが正常だろうが、終了したときには、sleep がすべて終了する（上限に当たらなくても、今回だと sh が wait していないのでこれに該当する）。
  - そのため、sleep プロセスたちが `myns.rs` 実行後には残っていない状態になる。全部がきれいにクリーンされている。

- 同じく、cgroup で CPU の利用についての制限をいれるため `cpu.max` に使えるCPU時間を定義した。
  - 上限を超えたときに、プロセスが殺されたりするのではなく、単にそのプロセスをCPUに割り当てるのを待たせる動きになる。
  - よって、CPUを使える時間が制限される。
  - 別件だが、今回 CPU を使い続けるスクリプトとして `timeout 5 sh -c 'while :; do :; done'` のようなスクリプトを実行した。ところが、タイムアウトがされずにずっとループが回り続けた（その間もCPU利用率は設定したとおりに制限されていたことを `top` コマンドで確認した）。
    - このときの `sh` は pid=1、つまり init process として動いていた。
    - 実は、PID namespace の init process に送れるシグナルは、init process がシグナルハンドラーを定義したシグナルに制限される。
    - 今回はシグナルハンドラーを定義していないので、`timeout` が SIGTERM を送れなくてタイムアウト処理が動かなかった。
    - init process は先述の通り、終了するとその namespace のプロセス全体が終了してしまうので、このような制限を入れているらしい。
    - なお、SIGKILL, SIGSTOP はそもそもシグナルハンドラーを定義できないシグナルなので、PID namespace の中からは SIGKILL, SIGSTOP は絶対に送れない。
    - ただし、namespace の外側のプロセスからであればシグナルは送れる。

- `seccomp` を使って、プロセスから呼ぶことのできる syscall を制限することを学んだ。
  - やることは、フィルターを定義して、そこにルール（どんな syscall を許可・禁止するか）を追加し、そのフィルターをカーネルに登録するだけ。
  - そのフィルターをもとに、カーネルが syscall 呼び出しをチェックしてくれる。
  - `myns.rs` では、`sh -c 'echo hello'` という単純なコマンドが成功するようにできるだけ最小限の syscall だけを許可するようなコードを書いた（本当に最小限かは別途確認が必要だがそこまではやっていない）。
    - 結局、16個の syscall を許可して動いた。
    - 本来の仕事に必要なのは `write` だけだった。
    - ほかは起動と終了のお膳立て（`execve`, メモリ、glibc の起動準備、`exit_group` ）だった。
  - 途中で glibc のエラーが出て少し悩まされた。
    - 必要なのに許可しきれていない syscall があるときに、glibc が `exit_group` を呼んで終了しようとするが、この `exit_group` 自体を許可していなかった。
    - `exit_group` の後の処理は基本的に想定されていないので、プロセスが終われないまま次の命令に進み、でたらめなアドレスを触って SIGSEGV が無限に出続けるというものだった。
    - 無限にエラーになってしまう問題は、`exit_group` を許可するだけで解決した。
    - 根本のエラー自体は、メッセージが「 Cannot allocate TLS block」と出ていたのでメモリ不足に見えたが、単に `arch_prctl` という syscall を許可していないだけだった。許可したら解決した。
