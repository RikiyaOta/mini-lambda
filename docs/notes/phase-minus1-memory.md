## Step 1: 自分のアドレス空間を印字する

**作るもの**: 自分自身のメモリ地図を、人間が読める形で表示するコマンド。

### 読むもの

`man 5 proc` の `/proc/[pid]/maps` と `/proc/[pid]/status` の項。

```
/proc/self/maps          1行1マッピング:
                         アドレス範囲 / 権限 / オフセット / デバイス / inode / パス
/proc/self/status        VmSize: (仮想サイズ) と VmRSS: (物理に載っている分) の行がある
/proc/self/smaps_rollup  上を集計済みにしたもの(答え合わせ用)
```

### やること

1. `/proc/self/maps` を読んで、各行を **サイズ付き** で表示する
   (アドレス範囲は16進なので引き算する)
2. 全マッピングのサイズ合計と、`/proc/self/status` の `VmSize:` を突き合わせる
3. `VmRSS:` も表示して、**仮想と物理の比**を出す

新しい API はほぼ不要。`std::fs::read_to_string` と `u64::from_str_radix(s, 16)` で足りる。

### 罠A・B・C の答え (2026-09-16、証拠付きで確定)

#### 罠B: `---p` は **ガードページ**

隣の領域を守るための壁。踏むと **SIGSEGV で即死**する(`myrun` Step 3 で見た終了コード 139)。
**静かに壊れるより、その場で確実に死ぬほうがマシ**、という思想。

サイズが 4 KiB なのは「ページフォルトの単位だから」ではなく、
**権限(`r`/`w`/`x`)はページテーブルの1エントリ = 1ページ単位でしか設定できないから**。
1バイトの壁は作れず、最小の壁がちょうど1ページになる。
(`maps` で ELF が `r--p` / `r-xp` / `rw-p` に割れているのも同じ理由)

**なぜ「隙間」ではダメで、わざわざ `---p` を貼るのか** ← ここが肝:
隙間も踏めば SIGSEGV になるが、**隙間はあとから `mmap(NULL, ...)` に埋められる可能性がある**。
`---p` で明示的にマッピングすれば、そのアドレスは「使用中」として予約され、**壁であり続けることが保証される**。
「使えないメモリを確保する」のは、アドレス空間という**場所取りゲームでの陣取り**だった。

**作られる瞬間を strace で捕まえた**:

```
mmap(NULL, 12288, PROT_READ|PROT_WRITE, ...|MAP_STACK) = 0x723201641000   ← 12 KiB 確保
mprotect(0x723201641000, 4096, PROT_NONE)              = 0                ← 先頭1ページを ---p に
sigaltstack({ss_sp=0x723201642000, ss_size=8192}, NULL) = 0               ← 残り 8 KiB を使う
```

`0x...641000 + 4096 = 0x...642000` でぴったり。正体は
**Rust ランタイムがスタックオーバーフロー検出用に用意する予備スタック(sigaltstack)**。
スタックが溢れて壁を踏むと SIGSEGV が飛ぶが、そのハンドラを動かすにも壊れていないスタックが要る。

#### 罠A: `[heap]` を作るのは `brk`

`strace -e trace=brk,mmap ./target/debug/mymem` で確認:

- `brk(NULL)` = 「今の program break はどこ?」の**問い合わせ**。`brk(0x...)` = 「そこまで動かして」の**指示**
- **`[heap]` の start = 最初の break、end = 動かした後の break**。
  実測 `0x5c7b6d1b0000 - 0x5c7b6d18f000 = 0x21000` = 132 KiB でぴったり一致
- `brk` にできるのは **1つの数字を上下させることだけ**

**`[heap]` が現れないプログラム**: `brk` を一度も呼ばず、すべて `mmap` で済ませる `malloc` 実装を使っているもの
(`musl` libc、`jemalloc`、`mimalloc` など)。
カーネルが `[heap]` と名札を付けるのは **`brk` で作られた領域だけ**なので、全部 `[匿名]` として並ぶ。

#### 罠C: 毎回変わるのは **アドレスだけ**。原因は ASLR

**ASLR (Address Space Layout Randomization)** = 起動のたびにレイアウトの位置をランダムにずらす仕組み。
攻撃者が「libc のあの関数はこのアドレス」と決め打ちできないようにするため。
**サイズ・権限・順番は変わらない。**

`setarch -R` で無効化すると設計値が見える(gdb がデフォルトで ASLR を切るので、
`0x555555555000` や `0x7ffff7...` は見慣れた値になる):

```
ASLR あり: heap→mmap 16.64 TiB / mmap→stack 11.50 TiB   ← 毎回変わる
ASLR なし: mmap→stack 127.9 MiB                          ← 設計値
```

### 深掘りで分かったこと (2026-09-16)

#### ページ / 仮想ページ / 物理ページ

- **ページ** = メモリを区切る固定サイズの区画。x86-64 は **4096 バイト**。
  1バイトずつ管理すると対応表がメモリより大きくなるので、4096倍の粒度にして表を 1/4096 にしている。
  用途によっては 2 MiB / 1 GiB の **huge page** もある
- **仮想ページ** = 仮想アドレス空間を 4 KiB ごとに区切った1区画
- **物理ページ**(= **ページフレーム**)= 実際の RAM を 4 KiB ごとに区切った1区画
- **ページテーブル**が両者を結ぶ。結んでいるのは**アドレスではなく番号と番号**
- **VSZ = 用意した仮想ページの枚数、RSS = そのうち物理ページが結び付いた枚数**。
  Step 1 でずっと数えていたのはページの枚数だった

#### アドレスは「ページ番号 + オフセット」に分かれる

```
0x62acf8415000
  └───┬───┘└┬┘
   ページ番号 オフセット(12ビット = 16進3桁)
```

- 4096 = 2^12 なので、**下位12ビット = 16進3桁**がオフセット
- **変換で書き換わるのは上位のページ番号だけ。下位12ビットはそのまま通る**。
  だからページの中身の並びは崩れない
- マッピングの境目は必ずページの境目にある(**ページアラインメント**)ので、
  `maps` のアドレスは末尾が必ず `000`。**自分の30マッピング、例外ゼロで確認した**

#### `maps` とページテーブルは別物 ★重要

| | `/proc/self/maps` | ページテーブル |
| --- | --- | --- |
| 正体 | **VMA** (Virtual Memory Area) のリスト | CPU の変換表 |
| 誰が読む | **カーネル**(ソフトウェア) | **ハードウェア(MMU)** が直接読む |
| 粒度 | 1行 = 1つの連続範囲(自分の場合30行) | 1エントリ = **1ページ** |
| 中身 | 「この範囲にはこれを、この権限で貼る」という**約束** | 「仮想ページ番号 → 物理ページ番号」の**実際の対応** |
| `maps` で見えるか | これ自体 | **見えない** |

- **`mmap` が作るのは VMA のほう。ページテーブルにはまだ何も書かれない**
- 書かれるのは**ページフォルトが起きた瞬間**
- → **VMA = 予約表、ページテーブル = 実物の対応表。VSZ と RSS の差は、この2つの差だった**
- どちらもプロセスごと。CPU の **CR3** レジスタが「今のページテーブルの先頭」を指し、
  プロセス切り替えのたびにカーネルが差し替える。「アドレス空間が切り替わる」の実体はこれ
- ページテーブル自身も物理メモリを食う → `/proc/*/status` の **`VmPTE`** で見える
  (grep: VmSize 1273184 kB / VmRSS 7560 kB / **VmPTE 124 kB**)。
  **`fork` が重いのはこの表をコピーするから。だから `Command` は `CLONE_VM` を選んだ**

#### なぜ 128 TiB なのか — 「9」はページサイズから来ている ★

x86-64 の CPU は仮想アドレスの**下位48ビットしか使わない**。

```
48 ビット = 9 + 9 + 9 + 9 + 12
            └───┬───┘   └┬┘
          4段のページテーブル  オフセット
```

- ページテーブルの1段は 4096 バイト(1ページ)、1エントリ 8 バイト
  → **4096 ÷ 8 = 512 = 2^9 エントリ** → 1段で9ビット引ける
- `2^48` = 256 TiB を上下に割って、**ユーザー空間が `2^47` = 128 TiB**、上半分がカーネル空間
- 64ビット全部使わないのは、段数が増えて変換が遅くなる割に誰も 16 EiB も使わないから。
  新しい CPU には5段(57ビット = 128 PiB)のモードもある
- **確認**: `[stack]` が `0x7ffffc226000`(ユーザー空間の上限 `0x7fff_ffff_ffff` のすぐ下)、
  `[vsyscall]` が `0xffffffffff600000`(**上半分 = カーネル側**)。桁が違った理由がこれ

#### `brk` と `mmap` の違い

| | `brk` | `mmap` |
| --- | --- | --- |
| すること | **既にある1つの島の右端**を動かす | **空き地に新しい島を作る** |
| 島の数 | 1本のまま | 何本でも |
| 場所 | 選べない(break の位置) | どこでもよい |
| 途中だけ返す | **できない**(端からのみ) | **できる**(`munmap`) |
| ファイル | 貼れない | 貼れる(任意。`MAP_ANONYMOUS` なら fd 不要) |
| `maps` での名前 | **`[heap]`** | 無名(`[匿名]`) |

- **`mmap` は `brk` の上位互換**。`brk` が残っているのは歴史的理由
- **`mmap` はデータセグメントを広げない**。program break は動かないまま、まったく別の場所に島を作る
- **アドレス空間は「1本の連続した範囲」ではない**。128 TiB のうち使用中は 0.000007% で、
  マッピングは広大な空白に浮かぶ**島**。実測で `[heap]` と `libc` の間に 124 TiB 空いていた

#### セグメント と program break、`[heap]` と「ヒープ」

- **セグメント** = ELF の「メモリへの貼り方の単位」。text(コード) / data(初期値あり) / bss(初期値なし)。
  (x86 CPU の「セグメントレジスタ」とは**別概念**。同じ言葉が違う意味で使われている)
- **program break** = bss の末尾。`brk` はここを押し上げる。できた空き地が `[heap]`
- → **ヒープは「データセグメントの続き」**。bss そのものではない
  (bss はコンパイル時に大きさが決まる固定区画、ヒープは実行時に伸び縮みする)
- **`malloc` はシステムコールではなく libc の関数**(`man 3 malloc` の 3)。
  毎回カーネルに聞くと遅いので、**大きくもらって細かく配る**。`BufReader` と同じ構造
- → **「ヒープ」の実体は `[heap]` と `[匿名]` に分散している**。`[heap]` はヒープの一部にすぎない。
  glibc は **128 KiB 超の要求を最初から `mmap`** で取る(`MMAP_THRESHOLD`)。
  Rust なら `Box::new(42)` は `[heap]`、`vec![0u8; 1_000_000]` は `[匿名]` に置かれる
- **断片化**: `[xxyyyyxxx]` のように真ん中が空いても、`brk` は端しか動かせないので返せない。
  `mmap` なら真ん中の1本を `munmap` で丸ごと返せる。
  → **希少なのは番地ではなく物理メモリ**。仮想アドレスは 128 TiB 余っているので実質ノーコスト

#### アドレス空間のレイアウト — 教科書の図にはゾーンが1つ足りない ★

```
高位 ┤ [stack]        ↓ 下へ伸びる
     │   (空き 約128 MiB + ASLR のランダム分)
     │ mmap 領域      ← libc、[匿名]、スレッドスタック。↓ 下へ伸びる
     │   (空き 数十 TiB)
     │ [heap]         ↑ 上へ伸びる (brk)
     │ bss / data / text
低位 ┤
```

自分の出力がそのままこの順番だった:
`5c7b68817000` mymem → `5c7b6d18f000` [heap] → `785f47600000` libc → `7ffffc226000` [stack]

- **stack が下に伸びるのは CPU 命令の仕様**。x86 の `push` は `RSP` を**減らして**から書く
- **heap が上に伸びるのは `brk` の定義**(データセグメントの末尾を押し上げる)
- **両端から中央に向かって伸ばす**ので、「ヒープに何 MiB、スタックに何 MiB」と**事前に配分を決めなくていい**。
  真ん中の空き地を早い者勝ちで分け合える
- **mmap 領域がスタックのすぐ下(約128 MiB)にあるのは設計**。
  **スタックには上限(`ulimit -s` 既定 8 MiB)があるから、その分だけ空ければ十分**。
  一方ヒープには上限がないので、残り全部を渡す。**伸びしろの要らないほうを詰めている**
- `ulimit -s unlimited` にすると基準点が決められないので、**legacy layout**(mmap をヒープの上から
  上向きに伸ばす古い方式)に切り替わる。実測で libc が 125 TiB 地点 → 12 TiB 地点へ移動した

#### なぜスタックだけサイズが決まっているのか ★

1. **バグを1プロセスの死で止めるため**。上限が無いと無限再帰がマシン全体を巻き込む。ガードページと同じ思想
2. **正常なプログラムは深くならない**。1フレーム数十〜数百バイトなので 8 MiB で数万段。超えたらほぼバグ
3. **スタックは連続していなければならない** ← 本質
   - 局所変数は「`RSP` から何バイト目」という**アドレスの引き算**でアクセスされる。
     「足りないので別の場所に飛ぶ」仕組みが CPU 命令レベルで存在しない
   - ヒープはバラバラの島でよい(`malloc` はアドレスを1つ返すだけ)ので、足りなければ `mmap` で島を足せる
   - → **連続した範囲を確保するには、あらかじめ「最大でここまで」と決めるしかない**
   - `brk` の「1本の連続領域は端からしか伸ばせない」と同じ制約。
     ヒープは `mmap` でこの制約を捨てられたが、**スタックは CPU の都合で捨てられない**
4. スレッドはそれぞれ自分のスタックを持つので、上限が無いとぶつかる。
   → スレッド生成時にサイズを決めて確保する(Rust のスレッドは既定 **2 MiB**、メインは `ulimit -s` の 8 MiB)

### Rust のメモ(演習の本筋ではないが引っかかった点)

- `&Mapping` 越しに `Option<String>` を `unwrap_or` に渡すと move になる(E0507)。
  → **`m.path.as_deref().unwrap_or("[匿名]")`**。`as_deref()` は `&self` から `Option<&str>` を作るので move しない。
  `clone()` は不要(表示するだけなら借りれば十分)
- **`nth(n)` はイテレータを消費する**。同じイテレータに `nth(0)` `nth(1)` `nth(5)` と呼ぶと位置が累積してずれる
- clippy `ptr_arg`: 引数は `&Vec<T>` より **`&[T]`**。
  (1) 呼び出し側の自由度が増える(`&v[..10]` や配列も渡せる) (2) 間接参照が1段減る
  (3) 「読むだけ」という意図に一致する。逆に長さを変えるなら `&mut Vec<T>` が正当。
  `String`:`&str` = `Vec<T>`:`&[T]` = `PathBuf`:`&Path` の関係。`&str` が「ポインタ+長さ」だったのと同じ形
- 桁揃えはやらない判断をした(学習に関係ない完成度に時間を使わない)。やるなら `{:>6}` で済む

### 使った道具: マッピングごとの実物を見る

`maps` は予約表だけだが、`/proc/self/smaps` は各マッピングに `Size:`(予約)と `Rss:`(実物)が付く。

```bash
awk '/^[0-9a-f]+-/ {name=$6; if(name=="")name="[匿名]"; perm=$2}
     /^Size:/ {size=$2}
     /^Rss:/  {rss=$2; printf "%8d KiB %8d KiB  %s %s\n", size, rss, perm, name}' /proc/self/smaps | sort -rn
```

> 後ろの「深掘りで分かったこと」は資料。ここが自分の理解の記録。

**1. `/proc/self/maps` は何の表か。ページテーブルとの違いは**

`/proc/self/maps` はカーネルが読み書きする、「この仮想メモリアドレス範囲にはこの役割をこの権限で割り当てる」
という予約表のようなもの。"役割"と書いたのはちょっと曖昧だけど、例えばある fd や、特にパスを指定しなくても大丈夫。
メモリアドレス範囲の予約をする。
ページテーブルは、仮想メモリと物理メモリの実際の対応が記録されたもので、これはカーネルではなく、
ハードウェア(CPU)が読み取るもの。
ページフォルトが起きる時に、`/proc/self/maps` の対応から、ページテーブルに実際にデータが記録されるのかな。

> ✅ 最後の一文は正しい。ページフォルトが起きるとカーネルは VMA を引いて
> 「この番地には何を入れるべきか(ファイルの中身か、ゼロ埋めか)」「どの権限で入れるか」を判断し、
> ページテーブルに1行書き込む。**予約表と実物対応表をつなぐのが、ページフォルトの瞬間。**

**2. VSZ と RSS は何を数えているか。差が生まれる理由**

VSZ = VmSize は、用意した仮想ページの枚数で、RSS は実際に物理ページに結びついた枚数。
差が生まれるのは、さっきのページテーブルの話がそのまま該当するね。
つまり、仮想メモリに割り当てられたけど、まだ実際にデータの読み取りが行われなくて、
ページフォルトが起きていなければ、物理ページに割り当てがされないから、差がうまれる。

**3. ページとは何か。なぜ 4 KiB 単位か**

ページは、メモリを区切る固定サイズの区画のこと。
1バイト単位にしてしまうと、1バイトごとに対応を記録する必要があり、対応表がとんでもない大きさになる。
4KiB にすることで、1/4096 にしている。用途によってはもっと大きなページを用意することもあるらしい。

**4. `brk` と `mmap` の違い**

`brk` は仮想メモリの bss 領域の外側を伸縮させるもの。1つの島を伸縮させるイメージ。
`mmap` は仮想メモリの中に自由に新しい島を作ったり、その島を伸縮させたりするイメージ。
brk でできることは全部 mmap ができる。
brk だと大きなメモリを確保してしまうと、確保した領域の中途半端なところでメモリが free されても、
伸縮しかできないので、物理メモリを返却することができない無駄が発生する可能性がある。
mmap は効果的な仮想メモリを使うことができるメリットがある。

> ⚠️ 2点だけ訂正:
> - **`mmap` は「島を伸縮」はしない。** 新しい島を作るのが `mmap`、丸ごと消すのが `munmap`。
>   既存の島のサイズを変えるのは別のシステムコール(`mremap`)。
> - **最後の一文は前半と食い違っている。** 前半の「**物理メモリを返却できない**無駄」が正しい。
>   仮想アドレスは 128 TiB のうち 0.000007% しか使っておらず番地は余っているので、
>   `mmap` の利点は「仮想メモリを効率的に使える」ではなく **「不要になった物理メモリを OS に返せる」**こと。
>   希少なのは物理メモリのほう。

**5. ガードページは何を守っているか。なぜ「隙間」ではダメか**

プログラムのバグがあって割り当てられた範囲外のメモリにアクセスしても、カーネルが権限を `---p` にしておけば、
実際には読み書きができないので、メモリを壊すことなく安全にそのプロセスを落とすことができる。
隙間だと、他の mmap が埋めてくる可能性があり、やはり他の処理で使うメモリを壊す危険性がある。
明示的に「ここはガードページです」と宣言することに意味がある。用途を宣言するって感じだね。

**6. なぜ実行のたびにアドレスが変わるのか**

ASLR か。プログラムの起動のたびにメモリレイアウトの位置をランダムにずらす仕組みがあるんだよね。
攻撃者がメモリレイアウトを決めうちで悪用することを防ぐ狙いがあるらしい。

### 自分の言葉で (2026-09-20)

**1. 1 GiB を確保しただけでは `VmRSS` が増えないのはなぜか**

`mmap` での確保は、ただカーネルが「このメモリアドレスはこの目的や権限で予約する」というだけで、
物理メモリを割り当てる操作ではない。`VmRSS` は実際に物理メモリに割り当てられたサイズなので、
`mmap` しただけでは増えない。

**2. 読むだけでは物理メモリが増えないのはなぜか**

なにも書き込みせず読み込んだ場合、カーネルが、どうせゼロしか返さないということで、
ゼロページという、すべての仮想メモリで共通のページを割り当てる。だから物理メモリは増えない。
全部の仮想メモリが同じ物理メモリを参照しているから。

**3. `MADV_DONTNEED` は何を捨てて、何を残したか**

MADV_DONTNEED は、物理メモリを捨てた。つまり、`mmap` で確保して書き込んだことによって
物理メモリが割り当てられた領域があったら、その物理メモリの割り当てを解除する。
ただし、maps にはまだ残っているから、もしまた読み書きをする時があったら、物理メモリの割り当てからやり直しになる。

> ✅ 補足: 物理メモリと一緒に**書いたデータも消える**(ページ 9999 の `1` が `0` になった)。
> 「解放」ではなく「破壊的な操作」。`free` のつもりで使うと生きているデータが消える。

**4. `free` しても `VmRSS` が減らないのはなぜか**

free はカーネルではなく、ユーザー空間のアプリケーションの話。malloc と反対の操作。
free することで、malloc が「このメモリはもう使っていないから割り当てに使える」と判断できる。
もしある程度まとまった塊で free されたら、タイミングは覚えてないけど、実際に OS に返却したりする。

> ✅ 補足: 返却の条件は glibc の場合、`brk` 領域の**端**に 128 KiB 以上の空きができたら `brk` を縮める
> (`M_TRIM_THRESHOLD`)、128 KiB 超で `mmap` から取った塊は `free` 時に `munmap`(`M_MMAP_THRESHOLD`)。
> `free` は返却を**約束しない**、が正確なところ。

### `unsafe` である理由(`mmap_anonymous` / `ptr::write`)

Rust の `unsafe` は「危険な操作」ではなく、
**「コンパイラには検証できない約束があるので、守る責任を人間が引き受けます」という宣言**。
`fork` のときは「子では async-signal-safe なものしか呼ばない」だった。`mmap` の場合は:

1. **既存のマッピングを黙って破壊できる** — 第1引数でアドレスを指定して `MAP_FIXED` を付けると、
   そこにあるマッピングが問答無用で置き換わる。自分のコード領域やスタックも消せる。
   (先週 strace で見た、動的リンカが libc を貼るときの `MAP_FIXED` がまさにこれ)
2. **返るのは生ポインタ** — 何バイトあるか、どんな型か、いつまで有効かを Rust は知らない。
   `munmap` 後に使えば未定義動作
3. (ファイル版)**中身が勝手に変わりうる** — `&[u8]` として読んでいる最中に他プロセスが書き換えると
   「不変参照の中身は変わらない」が破れる。truncate されれば SIGBUS

> **`unsafe` は「あなたの呼び方が安全か」ではなく「この関数が最悪どこまでできるか」で決まる。**

### Rust のメモ

- **`ptr::write<T>(dst: *mut T, src: T)` が書くバイト数は `size_of::<T>()`。ポインタの型 `T` が決める**
  - `*mut u8` なら 1 バイト、`*mut [u8; 4096]` なら 4096 バイト。同じ関数が型次第で変わる
- **`add(n)` は「n バイト進む」ではなく「要素 n 個分進む」**(`n * size_of::<T>()` バイト)。
  `*mut u64` にすると静かに8倍ずれる。C の `char*` と `int*` のポインタ演算と同じ規則
- **`add` は累積しない。** 新しいポインタを返すだけで、元のポインタは動かない
  (`base.add(1)` の次に `base.add(2)` は base+3 ではなく base+2)。
  累積したいなら `p = p.add(1)` と代入し直す。
  毎回 `base.add(i * 4096)` と基準点から計算し直す書き方のほうがずれなくて安全
- `NonNull<c_void>` は型が不明なメモリなので、書き込む前に `.as_ptr().cast::<u8>()` などで型を決める

### 自分の言葉で (2026-09-20)

**1. `fork` は何をコピーして、何をコピーしないか**

`fork` がなにをコピーするかは、プロセスのメモリや現在のスレッド、そしてページテーブルを基本的にはコピーする
(`CLONE_VM` でなければ)。実際の物理メモリ上のデータはコピーされない。
ただし、ページテーブルのデータだけ、たとえ VMA に書き込み権限があっても、読み取り権限でコピーする。

> ✅ 補足: 冒頭の「プロセスのメモリをコピーする」は、正確には **メモリの台帳(VMA リストとページテーブル)をコピーする**。
> 中身(物理ページ)はコピーしない。台帳のうちページテーブルは「読み取り専用」に書き換えた状態でコピーされる。

**2. 子が書き込んだとき、何が起きるか**

子プロセスが書き込んだ時には、CPU が「書き込み権限がない」とエラーを出すことでページフォルトが発生する。
カーネルが、VMA を見て、これは書き込み権限があるはず、つまり Copy on Write だなと判断して、
新しい物理ページにコピーをして書き込みする。この時点で初めてデータコピーが行われる(まさに copy on write)。

**3. `Rss` と `Pss` の違い。なぜ `Pss` が要るのか**

Rss は各プロセスから見た、物理メモリに割り当てられている大きさ。Pss はプロセスで割ったサイズ。
各プロセスからのものだけ見ていると、Rss だけを見て合計してしまうと、
実際より多くの物理メモリが割り当てられているように見える。
プロセス数で割ることで、本当に割り当てられている物理メモリが見えてくる。

> ✅ 補足: 割るのは**共有しているページだけ**(私有ページはそのまま数える)。
> 全プロセスの `Pss` を足すと、実際に使われている物理メモリと一致する。

## Step 4: 仮想アドレス → 物理アドレスを自分で引く 🔶 進行中(2026-09-20)

**確かめること**: Step 1 で「ページテーブルは `maps` には出ない、CPU が読むもの」と整理したが、
カーネルは読み出し専用の窓 **`/proc/self/pagemap`** を用意している(`man 5 proc`)。
これで「仮想ページ番号 → 物理ページ番号(PFN)」を自分で引く。Phase 3 の EPT に一番近い場所。

### `pagemap` の読み方

バイナリファイル。**仮想ページ1枚につき 64 ビット(8 バイト)のエントリ**が仮想ページ番号順に並ぶ。

```
仮想アドレス V のエントリの位置 = (V / 4096) × 8 バイト目
```

`File::open` → `seek` → `read_exact(8)` → `u64::from_le_bytes`。

| ビット | 意味 |
| --- | --- |
| 63 | **present** — 物理ページが割り当たっているか |
| 62 | swapped |
| 61 | file-page または shared-anon |
| 56 | exclusively mapped |
| 54〜0 | **PFN (Page Frame Number = 物理ページ番号)** |

**★ PFN は root でないと読めない**(Linux 4.2 以降、`CAP_SYS_ADMIN` が無いと 0 に塗りつぶされる。
物理アドレスの漏洩防止)。一般ユーザーで試したら `present=1 pfn=0x0` だった。
→ `sudo ./target/debug/mymem step4`(`cargo run` を sudo で包まない)

### 4-1: 1ページの PFN を、触る前と後で引く

1. 1ページ(4096 B)を `mmap_anonymous`
2. **触る前**: pagemap エントリの `present` と PFN を表示
3. 1バイト**読む** → 表示
4. 1バイト**書く** → 表示

**予想を先に**:
- [ ] 3回の表示で `present` と PFN はどう変わるか
- [ ] 2(読んだ後)と 3(書いた後)で PFN は変わるか。3 の PFN は「特別な値」か

**予告する罠**:
- [ ] `sudo` 無しだと PFN が全部 0。`present` が立っているのに PFN=0 なら権限の問題
- [ ] `read_to_string` は使えない(バイナリ)
- [ ] `/ 4096` と `× 8` の順番

**4-1 / 4-2 の結果 (2026-09-22)** ✅:

```
                     present    PFN
①触る前              false          0
②1バイト読んだ後     true     1238134   ← 3回実行しても、別プロセスでも同じ番号 = ゼロページ
③1バイト書いた後     true     1856335   ← 毎回違う番号 = その時空いていた物理ページ(CoW で付け替え)
```

- `1238134` は**このマシンのゼロページの物理ページ番号**。Step 2 で「システム全体で1枚」と説明したものが番号で確認できた
- ②→③で **PFN が変わる** = 読んだときはゼロページ(読み取り専用・共有)を指していて、
  書いた瞬間に CoW で新しい私有ページに付け替えられた。Step 2 と Step 3 の仕組みが1ページの番号の変化として直接見えた
- **罠に実際に踏んだ**: `sudo` 無しだと `present` は正しく立つのに PFN だけ 0。「動いているように見える」ので気づきにくい
