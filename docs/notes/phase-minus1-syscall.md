## 分かったこと

### `open` の第3引数 `mode` の罠

最初 `Mode::S_IWUSR` だけを渡していたため、`0o200`(所有者に書き込みのみ)でファイルが作られ、
**自分で作ったファイルを自分で読めない**状態になった。`cmp` が `Permission denied` で
失敗していたのに、`sudo cmp` で確認してしまい成功したと誤認した。

- `mode` は **新規作成のときにしか適用されない**。既存ファイルを上書きする場合は既存のパーミッションのまま
- 実際に作られるのは `mode & ~umask`(この環境の umask は `0002`)
- 検証コマンドを `sudo` で実行すると、権限の問題を握りつぶしてしまう

> ✅ 確認済み: `chmod 600` したファイルに上書き実行しても、パーミッションは 600 のまま変わらない

### `OwnedFd` と `close`

`nix::fcntl::open` は `std::os::fd::OwnedFd`(nix の型ではなく標準ライブラリの型)を返す。
スコープを抜けると `Drop` で自動的に `close` される。C では `close` 忘れが fd リークになるが、
Rust では所有権が引き受けている。`nix::unistd::close` の引数が `IntoRawFd` で
所有権を奪う形になっているのも、二重 close を型で防ぐため。

### `read` と `write` の非対称性 ★重要

どちらも「要求より少ないバイト数を返すことがある」が、**意味が違う**。

- **`read` が `n` バイト返した** → 正常。残りは次の周回で読めばよい。`&buf[..n]` で足りる
- **`write` が `m` バイト返した (`m < buf.len()`)** → **書き残しが `buf.len() - m` バイトある**。
  ここで次の `read` に進むとそのデータは永久に失われる。**その場で書き切るループが要る**

これが `std::io::Write::write_all` の正体。生の `write` は頼んだ分を書くとは限らないのでラッパが要る。

> regular file 相手ではまず起きないので、対処しなくても動いてしまう。パイプ相手だと破綻する。

### `EINTR`

ブロック中の `read`/`write` にシグナルが届くと、カーネルは処理を打ち切って `EINTR` を返す。
これは**失敗ではなく「やり直して」の意味**なので、`?` で上に投げてはいけない。

仕様上の重要な保証:

> **`read`/`write` が `EINTR` を返すのは、1バイトも転送していない場合だけ。**
> 一部を転送した後にシグナルが届いた場合は、`EINTR` ではなく**転送済みのバイト数**が返る。

このおかげで「`EINTR` = バッファ全体を渡し直す」「`Ok(m)` = m バイト進んだ」と綺麗に二分でき、
二重書き込みにならない。ここが曖昧だと EINTR 処理はどこかで必ず壊れる。

- `sigaction` で **`SA_RESTART`** を付けるとカーネルが自動で再開するため `EINTR` は上がってこない。
  普段出会わないのはこのため
- ただし `SA_RESTART` を付けても再開されない syscall がある(`man 7 signal` の
  "Interruption of system calls and library functions by signal handlers" に一覧)

### 末尾再帰は Rust では最適化が保証されない

`write_all` を再帰で書いたので、実際にどうコンパイルされるか逆アセンブルして確認した。

```bash
objdump -d --disassemble=<write_all のシンボル> target/debug/mycp   | grep -c 'call.*write_all'
# => 2   (debug: 自分自身への call が2箇所 = 本物の再帰。スタックが積まれる)
objdump -d --disassemble=<write_all のシンボル> target/release/mycp | grep -c 'call.*write_all'
# => 0   (release: 最適化でループに変換された)
```

末尾再帰なので原理的にはループに変換できるが、**Rust は末尾呼び出し最適化を保証しない**。
debug ビルドでは `call` が残る。「入力によって深さが決まる再帰」は、コンパイラの気分に
安全性を預けることになるのでループで書くのが定石。

Step 4 でバッファサイズを 1MB などに変えると、最悪 100万段の再帰になりスタックオーバーフローしうる。

### `write` が `Ok(0)` を返したらどうするか — errno に無いエラーの表現

`write_all` のループには「待つ手段」が無い。相手がブロックしてくれるなら1周待てば済むが、
`0` を即座に返し続ける相手だと **CPUを全力で回しながら再試行し続ける**(無音のハング)。
再帰版ならスタックオーバーフローで即死して気づけたが、ループ版は黙る。**落ちるバグより黙るバグの方が厄介。**

ただし `count > 0` で `0` が返るケースは `man 2 write` の規定に無い。書けない状況では
ブロックするかエラー(`ENOSPC` など)になる。該当しうるのは man が
`results are not specified` としている領域(行儀の悪いデバイスドライバなど)だけ。
**つまり実際にはまず起きない。「起きたら手に負えないので早く諦める」ためのガード。**

ここで詰まったのがエラーの表現方法。`nix::Result<()>` = `Result<(), Errno>` なので、
どれかの errno に嘘をつかせることになる。**適切な `Errno` は存在しない。**
errno はカーネルが返す番号だが、今回検出したいのは「規定外の状態にユーザー空間側が気づいた」
という自分の判断だから。

std がどうしているか確認した:

```
Error::from(ErrorKind::WriteZero) -> Kind(WriteZero)
  raw_os_error() = None                    ← 対応する errno が無い
Error::from_raw_os_error(5)       -> Os { code: 5, kind: Uncategorized, ... }
  raw_os_error() = Some(5)
```

`std::io::Error` は **OS由来(errno を持つ)と Rust由来(errno を持たない)の両方を表現できる型**
になっていて、`WriteZero` は後者。std は errno に無理やり当てはめることを避けている。
(逆に `EIO` の `kind()` が `Uncategorized` になるという逆方向のズレもある)

今回は演習なので `panic!` を選んだ。std が `Err` を返すのは**ライブラリだから**(呼び出し側から
回復の機会を奪えない)で、自分で使うアプリなら「ここに来たらおかしい」を素直に表現できる。
独自エラー型(`enum CopyError { Sys(Errno), WriteZero }`)を切るのが最も正直だが、
Phase 1 以降で `anyhow` / `thiserror` を通る道なので前倒ししない。

### Step 5-1: `copy_file_range` — データがユーザー空間を通らないコピー

`std::fs::copy` も `cp` も、`read`/`write` ではなく `copy_file_range(2)` を使っていた。

```
copy_file_range(3</tmp/src.bin>, NULL, 4</tmp/dst.bin>, NULL, ..., 0) = 10485760
copy_file_range(3</tmp/src.bin>, NULL, 4</tmp/dst.bin>, NULL, ..., 0) = 0   ← 0 = もう読むものがない(完了の合図)
```

`read`/`write` のデータの通り道は `src のページキャッシュ → ユーザーのバッファ → dst のページキャッシュ` で、
カーネルとユーザー空間の境界を2回跨ぐ。`copy_file_range` はカーネル内で
`ページキャッシュ → ページキャッシュ` を直接やるので、**プロセスは1バイトも触らない**。
実際 `user time` が `0.000s` になった。

### 速くなったのは 8% だけだった ★重要

1GiB で比較した(`results/phase-minus1-copy-methods.csv`)。

| 方式                              | sys time | 動かしたデータ |
| --------------------------------- | -------- | -------------- |
| `mycp`(64KB バッファ、read/write) | 約 0.453s | 2GiB           |
| `stdcp`(`copy_file_range`)        | 約 0.418s | 1GiB           |

データの移動量が半分になったのに、時間は 8% しか減らなかった。
`dst` を `/dev/null` にして read 側だけ測ると `sys 0.133s`。差し引くと内訳はこうなる。

| 内訳                                                                   | 時間      | 割合 |
| ---------------------------------------------------------------------- | --------- | ---- |
| dst 側(ページキャッシュのページ確保、ext4 のブロック割り当て、dirty 管理) | 約 0.320s | 71%  |
| src 側(ページキャッシュの検索 + バッファへのコピー)                     | 約 0.123s | 27%  |
| syscall 呼び出しそのもの(32768回 × 約300ns)                            | 約 0.010s | 2%   |

**支配的なのは「1GiB 分のページとディスクブロックを1つずつ作る仕事」で、これはどの方式でも減らない。**

Step 4 で出した「バッファを大きくしても頭打ちになる」という結論自体は正しかったが、
理由として書いた「データコピーのコストが変わらないから」は**帰属が違っていた**。

> ⚠️ `BufReader` の節にある `3.26GiB/s` は「memcpy の速度」ではなく「コピー処理全体の速度」。
> 10MiB では sys time が 0.006s しかなく、内訳を分解する解像度が無かった。
> 測りたい差の大きさが変わったら、測定の設計も変える必要がある(10MiB → 1GiB にして初めて見えた)。

### `real ≈ user + sys` だった = ディスクを一度も待っていない

1GiB 書いたのに `real 0.418 = user 0.000 + sys 0.418`。待ち時間がゼロ。
書いたデータはページキャッシュに載っただけで、**実際のディスクへの書き出し(ライトバック)は
プロセス終了後にカーネルが非同期でやっている**。Step 4 から Step 5 まで、一度もディスクの速度は測っていない。

### Step 5-2: `cp` は reflink を勝手に試している

```
openat("/tmp/dst.bin", O_WRONLY|O_CREAT|O_EXCL, 0664) = 4
ioctl(4</tmp/dst.bin>, BTRFS_IOC_CLONE or FICLONE, 3) = -1 EOPNOTSUPP (Operation not supported)
```

`--reflink` を指定していないのに `FICLONE` を試している。`cp` のデフォルトが `--reflink=auto`
(試して駄目なら通常コピーに落ちる)だから。`cp --reflink=always` も同じ `EOPNOTSUPP` になった。

**reflink** は「dst の中身を、src と同じディスク上のブロックを指すようにする」コピー。
成功すればデータは1バイトも動かず、上の内訳表の 0.32s も 0.12s も丸ごと消える。
書き換えが起きた瞬間に初めて実コピーする方式を **CoW (Copy-on-Write)** と呼ぶ。
この環境の ext4 は非対応(btrfs / XFS なら通る)。

> Phase 6 で「1つのメモリイメージから複数のmicroVMを起動する」ときに、まったく同じ発想が主役になる。

### strace は syscall 名より先に fd を見る

`lseek(0</dev/pts/1>, 0, SEEK_CUR) = -1 ESPIPE` を「コピー後にカーソルが末尾にあるから」と誤読した。
fd `0` は端末(標準入力)で、コピー対象のファイル(fd 3, 4)は2行前に閉じている。
`ESPIPE` は「端末やパイプには位置の概念がないので seek できない」の意味で、これは glibc の終了処理。
コピーとは無関係だった。**`strace -y` を付けると fd の横にパスが出る**ので必ず付ける。

なお `cp` の strace 175行のうち、実際のコピーは 13行だけ。残りは動的リンク・selinux 探し・locale 読み込みで、
これは「汎用コマンドであること」のコスト。

### `mycp` / `std::fs::copy` / `cp` の違い

|                | `mycp`                     | `std::fs::copy`            | `cp`                         |
| -------------- | -------------------------- | -------------------------- | ---------------------------- |
| dst の open    | `O_CREAT｜O_TRUNC`, mode 644 | `O_CREAT｜O_TRUNC`, mode 664 | `O_CREAT｜O_EXCL`, mode 664    |
| 権限の引き継ぎ | しない(常に644)            | `fchmod` で明示的に合わせる | open の mode 引数のみ        |
| dst の事前確認 | 無し                       | `statx` ×2                 | `O_PATH｜O_DIRECTORY` で存在とディレクトリ判定 |
| reflink 試行   | 無し                       | 無し                       | `ioctl FICLONE`              |
| 先読みヒント   | 無し                       | 無し                       | `fadvise64(POSIX_FADV_SEQUENTIAL)` |
| 本体           | `read`/`write` × 2n回      | `copy_file_range` × 2      | `copy_file_range` × 2        |

- **`std::fs::copy` が `open` に mode を渡した上でさらに `fchmod` するのはなぜか。** `mode` は新規作成のときにしか効かない(Step 1 で踏んだ罠)。dst が既存でもコピー元の権限を引き継ぐと約束しているので、`fchmod` が要る。`cp` が `fchmod` しないのは逆に「既存ファイルの権限は変えない」のが仕様だから。同じ「コピー」でも約束が違う
- **`cp` の `O_EXCL`** は「既に存在したら失敗」。存在しないことは事前に確認済みなのにもう一度確かめるのは、確認から open までの隙間に誰かが同名ファイルを作れるから(TOCTOU)
- **`fadvise64`** は「このファイルは先頭から順に読む」というヒントをカーネルに渡すもの。アプリがカーネルに意図を伝える syscall という種類がある。Phase 6 でゲストメモリを扱うとき `madvise` として再会する

## 自分の言葉で書く(到達点の確認)

> Step 3〜5 を終えてから、ここを埋める。**書けないなら理解できていない。**

### なぜアプリはディスクを直接触れないのか

カーネルに syscall で読み書きを依頼した時、カーネルはカーネル自身が持っているページというメモリに書き込むだけで、実際のディスクには触らない。読む時にはメモリに載っていなければディスクを読むけど。
ある程度の書き込みをまとめてディスクに非同期で書き込むようになっている。
また、そもそもディスクは全てのプロセスの共有物であり、各プロセスが好き勝手に書き換えられると、他のプロセスの処理を壊してしまうことができる。なので、ディスクの書き換え責務はカーネルに集約していて、アプリはさわれない。

### `BufReader` が存在する理由を、システムコールのコストの観点で

仮にプログラムが１バイトずつ読み取る処理を実行しようとした場合、素直に syscall を実行してしまうと、ユーザー空間とカーネルの切り替えコストが多く発生してしまう。CPUはずっとフル回転している。
そこで、プログラム側である程度処理をまとめて、１つの syscall にすることで効率化を図ることが BufReader のやっていること。
BufReader のデフォルトバッファサイズは 8KB だが、大きくすればするほど速くなるわけではないので注意が必要。実測したデータを元にすると、以下のことが言える：

- syscall 1回あたり 300ns かかるので、それ x 回数 だけの時間は、バッファを大きくすると減る。
- 一方で、データのコピーコスト（ 10MB のコピーは、 read,write で合計20MB）はバッファサイズを大きくしても変わらない。
- 実測したところ、20MiB のファイルコピーでかかった時間は、10MiB ファイルコピーのちょうど2倍であり、スループットがいずれも 3.26GiB/s で一致した。

実測データは [results/phase-minus1-bufsize.csv](../../results/phase-minus1-bufsize.csv) に記録した。
なお 300ns はこの環境(ネスト仮想化のGCPインスタンス)での実測値なので、絶対値としては信用しない。
データコピーのコストが変わらないので、バッファサイズをある程度以上大きくしても意味がなくなる。実測データでは、バッファサイズ64KB,1MBでsyscallは減っているのに sys time は変わらなかったことからわかる。

### `strace` で見えたシステムコールの説明

3本の比較は上の「`mycp` / `std::fs::copy` / `cp` の違い」の表にまとめた。
起動時の動的リンクなど個別の syscall の説明は Step 3 の記録で回収済み。
